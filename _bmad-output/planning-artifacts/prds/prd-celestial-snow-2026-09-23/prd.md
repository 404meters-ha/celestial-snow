# PRD · 技能交互 L2：AskUser 工具 + 任务暂停/恢复

> 背景层级：技能交互三层方案（2026-09-14 共识）——L1 预检表单已上线，本文定义 **L2 执行中询问**，L3 审批门为 L2 的两选项特例。
> 下游文档：架构设计 → 用户故事清单 → 分期实现。

## 1. 背景与目标

平台的技能与 AI 命令跑在无头 Agent（in-process cc-mini Engine）里，执行中遇到「只有用户能定的事」时目前只有两个坏选择：硬编码默认值，或直接停下来把结论丢给用户重跑。L1 预检表单解决了「提交前就知道要问什么」的问题，但依赖中间结果的问题（分析到一半才发现的分叉、写文件前的覆盖确认）无法前置。

L2 补上这一层：Agent 执行中可发起提问，任务进入**等待应答**状态，用户在 web 任务面板作答，任务带着答案恢复运行。

```
用户提交技能/AI命令 → Agent 执行 ──(无需问)──→ 正常完成
                        └─(需要问)→ 任务 waiting + 面板弹问题表单
                                        ├─ 用户作答 → 恢复运行（可多轮问）
                                        ├─ 用户取消 → Agent 收到取消，自行收尾
                                        └─ 超时/服务重启 → 任务失败，可重跑
```

**价值**：无头技能从「全自动或停摆」变为「全自动为主、关键点可协商」；L3 审批门（不可逆动作前确认）零额外机制获得。

## 2. 用户与场景

单人自用平台（无登录，user_id=1），与现有部署形态一致。

- 场景 A：技能执行到中途出现真分叉（如「issue 疑似已修复，仍生成课程还是换一个？」）→ 面板作答继续
- 场景 B：AI 命令栏分析时拿捏不准用户意图（如「你说的 pi 是树莓派还是 π 项目？」）→ 一次澄清换来精准结果
- 场景 C：Agent 即将做不可逆动作（覆盖已有文件、删除数据）→ 两选项审批门，用户放行才继续

## 3. 功能需求

### FR-1 AskUser 工具（引擎侧）

- 平台在 `agent_sdk` 自写 `AskUserQuestion` 工具（与 Claude Code / vendor 同名同义，技能正文双环境通用），挂载于**技能 invoke 与 AI 命令栏**两类运行；scaffold_build 不挂（无人值守）
- 输入 schema 对齐 vendor 惯例：1-4 个问题，每问含 question 文本 + 2-4 个选项（label/description）+ multiSelect（默认单选）；用户端始终可自由输入（等价 Other）
- **同批单问**：工具非只读，引擎单跑该工具——任一时刻一个任务最多只有一个待答问题
- 工具描述与系统提示词明确「何时该问」：仅限依赖用户偏好/授权的分叉；可查资料自答的不许问

### FR-2 任务暂停（waiting 态）

- 状态机扩为 `running | waiting | success | failed`；任务发起提问即 waiting，问题明细挂任务 payload（`pending_question`），进度时间线留痕（问了什么）
- 等待期吃 `skill_run_timeout` 同一额度（默认 3600s，不另设等待超时）
- 服务重启的孤儿清扫覆盖 waiting（同 running 一起置 failed「服务重启，任务中断」）
- elapsed 展示在 waiting 期冻结（不给人「卡死了」的错觉）

### FR-3 应答 API

- `POST /api/tasks/{id}/answer {"id", "answers": [...]}`：提交所选/所填（多问题一并提交，顶层 id = 待答问题 id）；任务非 waiting 态调用报 409
- `POST /api/tasks/{id}/answer {"id", "cancel": true}`：取消应答，Agent 收到 `is_error` 结果自行收尾
- 应答后任务回 running，时间线留痕（答了什么）

### FR-4 前端应答 UI

- 任务面板在 waiting 态内嵌渲染问题表单（单选/多选/自由输入，随 schema），提交/取消按钮
- waiting 态视觉区分（状态 tag + 耗时冻结）；1s 定向轮询与 3s 通用扫描均视 waiting 为「仍在跟踪」，页面刷新后可重新接管道
- 问题表单与日志区共存：先看到执行到哪，再作答

### FR-5 L3 审批门模式

- 审批门 = 两选项问题（「允许继续」/「取消」）的文档化用法，不建独立机制；前端可对审批形问题做轻量强调（如按钮主次）
- 写入技能作者指南：不可逆动作前必须问

### FR-6 冒烟技能

- 新增演示技能（如 `ask`）：跑通「执行中问 → 面板答 → 带答案续跑」全链，兼做 L3 模式示例；`ping` 保持零交互不动

## 4. 非功能需求

- 线程安全：提问/应答横跨 worker 线程与事件循环，遵循现有 JSON 列整体重赋值惯例
- 留痕：问题与答案均进任务时间线（封顶 200 沿用）
- 权限不变：AskUser 不经 PermissionChecker 放行逻辑（引擎 auto_approve 照旧），它本身就是向用户要权限的通道
- 边界测试沿用「项目根直跑断言脚本」风格，覆盖：非 waiting 应答 409、取消路径、超时回收、重启孤儿

## 5. 非目标（明确不做）

- 任意时刻暂停/恢复（要序列化引擎消息历史，另一个量级——2026-09-14 共识已排除）
- CLI 子进程路径的交互（技能已全部走 in-process Engine，无此路径）
- 多人抢答/答案仲裁（单人平台）；历史已完结任务的补答
- /tech 本期改造（用户拍板：冒烟技能验证，生产技能后续自然迁移）

## 6. 里程碑

| 期 | 范围 | 验收 |
|---|---|---|
| V1 | FR-1/2/3 + 边界测试 | curl 全链：发起任务 → waiting → answer → 成功；取消与超时路径 |
| V2 | FR-4/5/6 | web 面板真实作答全链 E2E；审批门模式示例可跑 |

每期独立可用、独立交付。

## 7. 风险

| 风险 | 缓解 |
|---|---|
| 模型滥用提问（事事都问） | 系统提示词硬约束 + 工具描述写明适用边界；单问串行天然限频 |
| 等待期服务重启丢问题 | 孤儿清扫置 failed，可重跑；时间线已有留痕可复盘 |
| 长等待吃满超时额度误杀 | 3600s 默认额度宽裕；面板实时显示剩余预算（实现细节归架构） |
| 前端状态 tag/轮询漏改 waiting | 状态机变更点枚举进故事验收（定向轮询/通用扫描/孤儿清扫/tag 映射） |
